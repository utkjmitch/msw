> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Authorized:** Jimmy, 2026-10-22, PC chat: "would like to start using the MSW package for projects if it's better / more efficient", then "let's rule, then launch."

**Goal:** Close the four gaps that keep MSW from being the factory's default site check. When this plan is built:

1. A read-only walk loads a site's data from Firestore and other read-only POST endpoints, and every write is still refused.
2. Failures caused by the walk itself or by the box's network are labeled **tool noise** and never counted as site findings.
3. `msw report` turns a run's signed events and findings into `REPORT.md` and into gate-item cards for Jimmy's cockpit.
4. A factory partial, `MSW-WALK.md`, means a walk goal no longer has to describe the setup.

The plan also settles the review of the D-1 drift rule (Task 5 and Task 6) and writes the Minister's Walk checklist (Task 10).

## Global Constraints

Plan A's constraints all still apply. These are added:

- **Read-only stays the default, and it stays read-only.** A read channel lets through only a `POST` that is not a page navigation and that matches a named shape (Task 1). `PUT`, `PATCH` and `DELETE` are never allowed through a read channel. A form submit is a navigation, so it is always `would-submit`. Every request a read channel lets through is a signed `read` event.
- **No write is allowed by default.** A journey with no `read_channels` field behaves exactly as it does today. A test in Task 2 proves that.
- **Tool noise is labeled. It is never deleted.** A record labeled `tool-noise` stays in `instrument.jsonl` and the signed log. It is not turned into a finding, no severity floor applies to it, and the report lists it in its own section.
- **`msw report` reads; it never walks.** It never launches a browser, never calls a model and never changes a walk folder. It writes `REPORT.md`, `cards.json` and `MINISTERS-WALK.md` next to the run, and nothing else.
- **Cards follow the decision-block contract.** Every card's text is a ```yaml decision block. `sourceRef` is repo-qualified (`msw:<path>`, exactly one colon). There are at most 12 cards per run, matching the cap of 10 to 12 decisions per sitting.
- **Public repository.** Plan B's tests and fixtures carry no real site data. Fixture pages are made up. Walk evidence follows D-2: only text evidence and the screenshots findings cite are committed.
- The box runs Node 20.20.2 and `package.json` asks for Node 22. Build, typecheck and all 82 tests pass on 20 (checked again on 2026-10-22 for this plan). Keep code that runs on both.

## Review Focus

1. **A Firestore page with both channels** (Listen and Write): the Listen POST goes through and the page shows its data, while the Write POST is refused as `background-write`. Test in Task 2.
2. **A read endpoint that redirects with 307 or 308** to another path: the redirect would carry the body on, so it is refused. Test in Task 2.
3. **A GraphQL endpoint named as a read channel that receives a `mutation`**: refused. One that receives a persisted query with no query text: refused, because its operation type cannot be read. Tests in Task 1.
4. **A console error that comes right after the walk blocked a request on the same page, but names a different host**: still a site finding. Noise needs a matching cause, not just a nearby one. Test in Task 3.
5. **A carousel link with the same name but a different target** (a strip of stories, each with a "Read the story" link): the drift rule refuses it after Task 5. Today the same name, role and twin count let it through. Test in Task 5.
6. **A client-rendered page whose text changes between the two arrival looks**: the Dead Parrot check still passes for an honest walk and still fails an act with no look. Test in Task 6.

**Files:**

**Interfaces:**
- Produces:
  ```ts
  // In a journey file:
  // read_channels:
  //   - preset: firestore-listen          # host defaults to https://firestore.googleapis.com
  //   - preset: firestore-rest-read
  //   - preset: graphql-query
  //     origin: https://api.example.org
  //     path: /graphql
  //   - origin: https://search.example.org  # a plain endpoint: one origin, one exact path, POST only
  //     path: /api/search
  export const ReadChannelZ: z.ZodType<ReadChannel>;
  export type ReadChannel =
    | { preset: "firestore-listen" | "firestore-rest-read"; origin?: string }
    | { preset: "graphql-query"; origin: string; path: string }
    | { preset?: undefined; origin: string; path: string; method: "POST" };
  export interface ReadRequest { method: string; url: string; body: string | null; navigation: boolean }
  /** The name of the channel that lets this request through, or null. Pure. */
  export function matchReadChannel(req: ReadRequest, channels: ReadChannel[]): string | null;
  ```
- The presets, exactly:

  | Preset | Origin (default) | Lets through | Never lets through |
  |---|---|---|---|
  | `firestore-listen` | `https://firestore.googleapis.com` | `POST` to a path ending `/google.firestore.v1.Firestore/Listen/channel` | `Write/channel`, anything else |
  | `firestore-rest-read` | `https://firestore.googleapis.com` | `POST` to `/v1/projects/*/databases/*/documents…` ending `:runQuery`, `:runAggregationQuery`, `:batchGet`, `:listCollectionIds` or `:partitionQuery` | `:commit`, `:batchWrite`, `:beginTransaction`, `:rollback`, `:write`, `:listen` (the streaming form) |
  | `graphql-query` | none (must be given) | `POST` to the exact path whose JSON body (or each item, for a batch) has a `query` string whose first operation is `query` or a bare `{` | a `mutation` or `subscription` anywhere in the document; a body with no readable `query` (a persisted query sent as a hash only); a body that is not JSON |
  | plain endpoint | must be given | `POST` to that exact origin and path | any other path, method or origin |

- Rules for every channel: the method must be `POST`; `navigation: true` never matches (a form submit is always `would-submit`); the origin is compared as `new URL(x).origin`; the path is compared exactly, except for the presets' own patterns.

### Task 3: Tool noise: label what the box and the walk caused (pure, then wired)

Closes gap 4, first half. Comunidad Connect had 148 `net::ERR_TUNNEL_CONNECTION_FAILED` records (the box's egress proxy) and 10 Firestore "Could not reach backend" errors (read-only mode). The severity floor made each a severity-3 "console error" finding (CC `REPORT.md`, instrument summary; McLaren item 2; PickProphets section "Not confirmed").

**Files:**
- Create: `server/src/instrument/noise.ts`, `server/tests/noise.test.ts`
- Modify: `server/src/walk/session.ts` (`record()` labels each record before it is signed)

**Interfaces:**
- Produces:
  ```ts
  export type NoiseCause = "egress" | "walk-block";
  export interface NoiseLabel { label: "tool-noise"; cause: NoiseCause; why: string; cause_event?: number }
  export interface BlockSeen { seq: number; url: string; page?: string; at: number }   // from blocked events
  /** Returns a label when the record was caused by the box's network or by the walk's own guard; otherwise null. Pure. */
  export function classifyNoise(r: InstrumentRecord, recent: BlockSeen[], now: number): NoiseLabel | null;
  ```
- The rules, exactly. Anything not listed stays a site record.

  | Record | Label when | Cause |
  |---|---|---|
  | `requestfailed` | error is `net::ERR_TUNNEL_CONNECTION_FAILED`, `net::ERR_PROXY_CONNECTION_FAILED` or `net::ERR_PROXY_AUTH_UNSUPPORTED` | `egress` |
  | `console` | text contains one of those three error codes | `egress` |
  | `requestfailed` | error is `net::ERR_ABORTED` or `net::ERR_FAILED`, and its URL equals a `blocked` event's URL in this walk | `walk-block`, `cause_event` = that event |
  | `console` / `pageerror` | a `blocked` event on the same page in the last 10 s whose host appears in the text, **or** a known signature for that host (the table below) | `walk-block` |
  | `http` 4xx/5xx | never noise (the site answered) | — |
  | `axe`, `vitals` | never noise; vitals measured through the proxy get a caveat in the report, not a label | — |

  Known signatures (a short table in `noise.ts`, each with a test):

## The D-1 drift-rule review

**Jimmy's ruling (2026-10-22):** "D-1: keep the drift rule for self-moving content, and review it in plan B."

**The question.** Keep the rule as it is, harden it, or replace it with region-aware hashing (a state hash that leaves out the parts of the page that move by themselves)?

**Recommendation: harden it (Tasks 5 and 6).** Keep the narrow rule. Add the link target to a control's identity, tell the Walker when the rule applies, and count it in the seal. Separately, fix the Dead Parrot check's definition of a page and settle the page before the arrival look. Do not build region-aware hashing.

**Evidence.**

1. **The rule did its job.** Plan A's server, without the rule, in Comunidad Connect pass 1: Ruth made 0 steps with 9 refusals, Marisol (Spanish) made 0 steps with 7 refusals, and the first Inspection failed at step 3. With the rule, in pass 2: 6, 11 and 11 steps, with 0, 3 and 0 refusals, and the Inspection passed (CC `REPORT.md`, run health and Inspection).
2. **What the rule actually pressed.** All 10 drift acts in the CC evidence (pass 2 and both Inspection attempts, read from `events.jsonl` on 2026-10-22): "Reject all" or "Rechazar todo" on the cookie panel 5 times, a menu link twice ("Get Involved", "Involúcrate"), "Open navigation menu" once, "scroll down" once, and the carousel tab "Go to item 2: July 2026 Bulletin" once. Each was a control that did the same thing before and after the page moved. None was pressed in error.
3. **The hole.** The rule matches a control by kind, role, full name, and its place among same-named twins. It does not look at where a link goes. The CC home page strip carries a "Leer la historia" link (4 occurrences in the Spanish walk's events) that shows a different story on each slide. If the strip turns between the look and the act, the rule as built presses the link for a story the Walker never saw. That did not happen in the evidence, but nothing stops it. Task 5 adds the link target to the identity and a test for exactly this case.
4. **Why not region-aware hashing.** It would leave the moving region out of the state hash. A link inside that region (the same "Leer la historia") would then change its target without changing the state, and spec 5.3 rule 2 ("act must follow a look of the same page state") would pass with no check at all. It is a weaker rule on exactly the controls that need it. It also needs region detection, which costs a second timed look on every page. A region that moves slower than the detection window, such as an 8-second carousel, would be missed.
5. **Where the real damage was: the Dead Parrot check, not the act rule.** Comunidad Connect had 12 of 12 walks `alive: false`, PickProphets 9 of 9, and McLaren Accord 2. Every failure was "1 screenshot" or "no instrument record" per state, caused by pages that change by themselves. Neither keeping nor replacing the drift rule touches that. Counting pages by address visit (Task 6) does, and it keeps every check that catches a faked walk.
6. **Still not fixed:** replays of moving pages rarely reach the same state (CC 11 of 35 reproduced, PickProphets 13 of 24). Settled arrival (Task 6) should help. A tolerant replay match is listed under "Not in plan B".

````markdown
# MSW-WALK: walking a site with the Ministry of Silly Walks (include-by-reference)

A walk goal says "Follow `/opt/goals/_partials/MSW-WALK.md`" and then gives only: the site, its address, the Walkers and journeys (or where to write them), the viewports and languages, and the branch. Everything else is here.

MSW sends AI Walkers (personas with a story, a patience budget and things that make them leave) through a real browser. The server shows them only a screenshot, the visible text and numbered options, and enforces the walk's rules. It never calls a model. You run the Walkers, then `msw report`.

## 1. Clone and build

```
git clone <msw remote> msw && cd msw/server        # in a box: the clone is already at /wt/msw/<your clone>
npm ci --no-audit --no-fund
npm run build
npm test                                            # must pass before you walk
```

The browser is preinstalled in boxes (`PLAYWRIGHT_BROWSERS_PATH=/ms-playwright`, Chromium build 1243 for Playwright 1.63.0). Never run `npx playwright install` in a box. Node 22 is asked for; Node 20 works (build, typecheck and tests pass).

## 2. Lay out the site

```
walks/<site>/walkers/<id>.yaml                 one dossier per Walker (formats/walker.schema.json)
walks/<site>/journeys/<walker>-<goal>.yaml      one per journey (formats/journey.schema.json)
walks/<site>/<YYYY-MM-DD>-<label>/run.json      the run: id, out_dir ".", environment {name, kind}, mask_personal_data: true
```

- Every journey runs on `phone` and `desktop`. Bilingual sites run in both languages.
- Read-only is the default. Never set `mode: transact` on a live site. Admin journeys run only on a test copy with seeded data.
- Validate before walking: `node -e` with `loadWalker` and `loadJourney` from `server/dist/formats/load.js`, or the site's `validate.mjs`.

### Read channels: sites that read data with POST

If the site loads its content from Firestore, GraphQL or a search API, read-only mode blocks those reads unless the journey names them. The page then renders empty, and the report says "read-only blocked N POSTs … add a read channel". Add only what the site uses:

```yaml
read_channels:
  - preset: firestore-listen           # Firestore's live channel (most Firebase sites)
  - preset: firestore-rest-read        # Firestore REST queries (runQuery, batchGet)
  - preset: graphql-query              # queries only; mutations are refused
    origin: https://api.example.org
    path: /graphql
  - origin: https://search.example.org # one exact POST endpoint
    path: /api/search
```

Writes stay refused: Firestore's Write channel, commits, GraphQL mutations, form submits, `PUT`, `PATCH` and `DELETE`. Each read let through is a signed `read` event, and the manifest lists the channels.

## 3. Start the server and run each Walker

A running Claude Code session cannot use an MCP server registered after it started. Run each Walker as its own headless session with only the msw tools:

```
cd walks/<site>/<run>
cat > mcp.json <<EOF
{ "mcpServers": { "msw": { "command": "node", "args": ["<msw>/server/dist/mcp/server.js", "--run", "$PWD/run.json"] } } }
EOF
timeout 1800 claude -p --mcp-config mcp.json --strict-mcp-config --tools "" --allowedTools mcp__msw \
  "<walk prompt: who you are (the dossier), your goal, start_walk(walker, journey, viewport, locale), and the rules below>" \
  > walks/<walker>-<journey>-<viewport>-<locale>.md
```

- Start the server from the run folder (`out_dir: "."` resolves from the server's working directory).
- One walk per session. Walkers never share a session, and the session writing the report is not a Walker.
- Tell each Walker: a "the page changed; look again" refusal is free, so look and try again. Rate at least two options and answer the four questions on every act. Write a finding (`note`) the moment something is wrong. Run away when your Walker would. Narrate in the first person.
- Wrap every session in `timeout`. A walk that hangs is a walk that failed; record it and move on.
- **Cost:** about $1.78 and 1.17M tokens (mostly cache reads) for eight sessions on one site (McLaren Accord, 2026-10-15). Run one Walker first and compare it with that before running the rest.

cd <msw>/server && node dist/cli/msw.js report ../walks/<site>/<run> --site "<Site name>"
```

## 5. Read the noise labels before you write a word

The server labels what the walk or the box caused. Labeled records are never findings:

| Label | Cause | Example |
|---|---|---|
| `tool-noise`, cause `egress` | the box's egress proxy refused a host | `net::ERR_TUNNEL_CONNECTION_FAILED` for `www.google.com` |
| `tool-noise`, cause `walk-block` | read-only mode blocked a request, and the page complained | Firestore "Could not reach Cloud Firestore backend" after a blocked Listen POST; "Failed to fetch" after a blocked chat send |

Not labeled, but read with care:

- Vitals (slow pages, layout shift) measured through the proxy are leads, not measurements.
- `ERR_NAME_NOT_RESOLVED` may be the box's DNS. Confirm from an ordinary connection before blaming the site.
- A hang or blank page is confirmed in a second browser (Playwright, with timings) before it is called a site bug (GOAL-RULES 4).
- `seal.json`'s `warnings` names any endpoint read-only blocked often enough to matter. Add a read channel and walk again rather than report an empty page.

````markdown
# The Minister's Walk

*The Ministry does not certify a walk that no human has taken.*

A person walks the site after the Walkers and before the report goes to the site's owner. That person is the site's owner, staff or a partner, named by role in the run's notes. They check two things: that the findings are real, and that the guide works for a person. It takes 30 to 60 minutes. You need the run's `REPORT.md` and `MINISTERS-WALK.md`, an ordinary computer and an ordinary phone, and an ordinary connection (not the box).

## Before you start

- [ ] Use your own phone and computer, on your own network. Do not use a factory box or a VPN.
- [ ] Use a private window, logged out, with no saved cookies for the site.
- [ ] Have the report open on another screen. Do not read the Walkers' narrations first; they will steer you.
- [ ] Write your role (not your name) and the date at the top of `MINISTERS-WALK.md`.

## 1. Walk the guide

If the run has a guide (`guide.md` or `inspection/guide-*.md`), follow it step by step, exactly as written, on the device it names.

- [ ] Tick each step that worked as written.
- [ ] At the first step that did not, stop and write what you saw. That is a finding about the guide or the site; say which you think it is.

## 2. Check each top finding

For each finding in the sheet:

- [ ] Go to the screen it names, on the device and in the language it names.
- [ ] Mark it **seen** (it happens to you too), **not seen** (it does not happen), or **not sure**.
- [ ] If it is not seen, note anything that might explain it: a slow connection, a cookie banner, the page having changed since the walk date.
- [ ] For any finding marked as possibly caused by the box (missing images, slow pages), check it especially. Your ordinary connection settles it.

## 3. Walk one goal as yourself

- [ ] Pick the journey closest to why a real visitor comes to this site. Try to reach its goal on your phone, without the guide.
- [ ] Note anything that got in your way that the report does not mention.

## 4. Rule

- [ ] **Share it as the before**: the findings marked seen go to the owner as they are.
- [ ] **Share with changes**: list the findings to drop or soften, and why.
- [ ] **Do not share yet**: say what must happen first (a re-walk, a fix to MSW).

Write `share: yes`, `share: with-changes` or `share: no` in the sheet's front matter, and commit the sheet. The next `msw report` reads it and updates the share card.
````
